# 02｜老人亲人拨号 App：软件逻辑 AI 提示词

版本：1.0｜日期：2026-09-17｜产品名：SilverPhone
配套：[总控](00_使用说明与总控提示词.md) · [UI](01_UI设计_AI提示词.md) · [功能](03_软件功能_AI提示词.md) · [技术栈](04_软件技术栈_AI提示词.md)

## 1. 给执行 AI 的任务

你负责把本应用实现成行为确定、状态清楚、数据不会在失败时损坏的本地 Android 工具。严格执行本文，不自行发明云同步、联系人智能合并、自动拨号重试、自定义挂断或跨版本迁移机制。

核心闭环：家属添加／导入亲人 → 本地保存 → 老人看照片单击拨号 → 系统电话接管 → 返回仍是原来的亲人首页。

本文中的“必须”是验收要求。“默认”是已确定的 V1 产品规则，除用户后续明确更改外不要重新设计。所有示例数据只用于测试，不得真实拨打。

## 2. 角色与数据边界

### 2.1 老人日常流程

允许：打开应用、纵向浏览、点一张亲人卡片拨号、正常返回。

不要求：登录、输入号码、选择 SIM 卡以外的 App 内分支、确认每次拨号、长按或双击、管理文件。

SIM 选择可能由系统要求；家属可预先在系统里设置默认语音 SIM。本应用不调用厂商私有接口绕过系统选择，也不承诺所有双卡机都绝对一步完成。

### 2.2 家属管理流程

普通点击两次进入设置。家属可以增删改、调整顺序、导入导出、设置字号和开启所需权限。这只是操作区分，不是账号权限隔离，不做密码或身份认证。

### 2.3 资料来源

仅允许三种来源：手工录入、本机系统通讯录明确选择、用户明确选择的本应用 ZIP 文件。不得后台扫描通讯录、读取聊天联系人或偷偷上传任何信息。

## 3. V1 领域对象与统一限制

### 3.1 联系人 Contact

| 字段 | 类型与规则 | 说明 |
|---|---|---|
| id | 小写、规范格式 UUID v4 | 跨设备保持身份；手工和系统导入新建时生成 |
| displayName | 非空字符串，1～12 个 Unicode 码点 | 老人对这个人的称呼，不是必须实名 |
| phoneNumber | 规范化字符串 | 一个卡片只绑定一个号码 |
| sortOrder | 0 起连续整数 | 首页先后顺序，升序显示 |
| placeholderColor | 六个固定枚举之一 | 无照片时使用；保存后保持不变 |
| photo | 可空的 Photo 值 | 对应一个本地照片记录；不存外部路径 |

六个占位色枚举：LIGHT_BLUE、LIGHT_AMBER、LIGHT_PURPLE、LIGHT_TEAL、LIGHT_ROSE、LIGHT_GRAY。默认 LIGHT_BLUE。家属可以选择，不使用随机颜色。

同一个号码可以有多张手工联系人卡，例如共用座机。号码建立普通索引，不建立唯一索引。同名也允许，但家属页提醒用照片或称呼区分。

### 3.2 照片 Photo

| 项目 | V1 规则 |
|---|---|
| 归属 | 每个联系人最多一张，按 contactId 关联 |
| 长期保存 | Room 中独立照片表的 JPEG BLOB |
| 图像形状 | 正方形，边长不超过 512 px，不放大低分辨率原图 |
| 单张存储大小 | 不超过 128 KiB，即 131072 字节 |
| 元数据 | 本应用生成照片不保留原图 EXIF、GPS、原文件名 |
| 缓存键 | contactId + 照片实际字节 SHA-256 |
| 无照片 | 不创建照片记录，使用持久化占位色和人物轮廓 |

使用独立照片表是为了避免首页列表查询一次读取所有图片，也使联系人与照片能使用同一个 Room 事务。V1 不同时维护一套长期照片文件库。

### 3.3 本机设置

- fontPreset：STANDARD、LARGE、EXTRA_LARGE、HUGE；对应 1.0、1.2、1.4、1.6，默认 LARGE。
- contactsRevision：从 0 开始的非负 Long。每次成功改变联系人、照片或顺序的事务只增加一次；字号调整不增加。
- 拨号权限、通讯录权限以系统实时结果为准，不能用一个数据库布尔值冒充权限状态。
- 不存储未完成的拨号请求，不保存“回到前台后自动继续打电话”的待办。

### 3.4 容量和输入上限

| 项目 | 上限 |
|---|---:|
| 本地联系人卡数 | 500 |
| 一次导入文件中的联系人 | 500 |
| 外部原始照片文件 | 20 MiB |
| 外部原始照片像素数 | 2400 万像素；预览仍必须采样读取 |
| manifest.json | 1 MiB，UTF-8 |
| 导入 ZIP 实际文件大小 | 80 MiB |
| ZIP 解压后的实际累计内容 | 70 MiB |
| ZIP 条目数 | 501，即一个 manifest 与最多 500 张照片 |
| 单张归档照片 | 128 KiB；512 × 512 px 以内的正方形 JPEG |
| 输入姓名 | 12 个 Unicode 码点 |
| 号码数字部分 | 3～20 位，开头可有一个 + |

MiB = 1024 × 1024 字节，KiB = 1024 字节。以上容量是工程默认限制，不是 Android 平台的固有限制。不得仅信任文件提供者或 ZIP 声明的大小，读取时必须实时计数。

## 4. 启动、导航与返回

1. 启动后异步读取 Room 设置与联系人元数据。
2. 正常有数据时直接展示首页，默认排序为 sortOrder。
3. 没有联系人时展示真实空状态，让家属添加；不插入可拨打的演示号码。
4. 数据读取失败和“联系人为零”必须区分；失败不能触发自动重建空库。
5. 不自动弹出所有权限。首次添加照片、读取通讯录和开启拨号各自按需触发。
6. 管理页面完成后回到首页，看到刚保存的数据。
7. 从系统电话回到 App，保留页面滚动位置；不恢复任何待拨事件。
8. 冷启动／进程重建始终没有待执行拨号。可恢复表单文字草稿，但不能恢复自动呼叫。
9. 未保存编辑离开时询问放弃；没有修改则直接返回。
10. 导入提交事务期间防止重复进入管理操作；进程退出依靠数据库事务保证一致性。

## 5. 拨号流程：只发起一次真实请求

### 5.1 正常前提

联系人存在、号码有效、CALL_PHONE 当前已授权、设备存在可响应的电话能力。在此条件下，一次点击使用 ACTION_CALL + tel URI 交给系统，不打开自定义确认页。

ACTION_CALL 与 ACTION_DIAL 含义不同：前者请求直接发起电话，需要 CALL_PHONE；后者仅打开拨号界面。不能静默用后者代替验收中的直接拨号。[Android 官方普通电话 Intent 说明](https://developer.android.com/guide/components/intents-common#Phone)

### 5.2 状态定义

| 状态 | 允许事件 | 下一步 |
|---|---|---|
| READY | 点击一个有效联系人 | 同步关上本次启动门闩，进入 CHECKING |
| CHECKING | 重新读出联系人并检查当前权限 | 合法则 DISPATCHING；否则 HELP／ERROR |
| DISPATCHING | 前台宿主发送一次 Intent | 成功交给系统则 HANDED_OFF；异常则 ERROR |
| HANDED_OFF | 系统电话界面运行／返回 | 回到前台后解除门闩；必须新点击才再次拨打 |
| HELP | 家属处理权限问题 | 返回 READY，不自动拨打旧联系人 |
| ERROR | 用户关闭或返回 | READY；不自动重试 |

这些状态只表示本应用对请求的处理，不表示电话已接通、正在通话或已挂断。

### 5.3 点击防重与生命周期

- 点击处理进入主线程串行事件路径，先设置门闩再执行异步检查。
- 一次有效点击生成一个仅存在于当前进程的事件标识。
- 门闩关闭时忽略后续点击，包括另一个联系人；不排队、不最后一次覆盖第一次。
- 附加至少 1000 ms 的请求间隔，只用于防止同一手势／连点重复，不在 UI 增加倒计时。
- Composable 重组、Flow 再次发值、横竖屏变化、Activity 重建不能重新发出 Intent。
- Intent 只能由处于合适前台生命周期的宿主消费一次；不得在绘制函数中直接启动电话。
- 已交给系统后，正常离开并返回前台时恢复可点状态。若没有观察到窗口切换，3 秒后只解除启动门闩，不推断接通或失败，不自动重发。
- 系统异常或权限检查失败时释放门闩，展示相应帮助，不一直锁住首页。
- 进程重建丢弃旧事件。用户需要重新点击才能拨号。
- 滑动卡片列表、取消触摸、滚动途中抬手不产生点击，交给成熟 Compose 点击／滚动语义处理。

### 5.4 权限不足

1. 老人点卡发现缺少 CALL_PHONE，停止本次请求，显示简短帮助。
2. 不把联系人 ID 保存成授权完成后继续拨打的命令。
3. 家属在设置里点“开启拨号权限”后才请求权限。
4. 允许后回到首页提示“已开启，再点亲人照片打电话”。
5. 拒绝后不反复弹框；系统不再显示权限框时提供 App 系统设置入口。
6. 从系统设置回来重新检查实际权限；无变化也不循环跳转。
7. 后续系统撤回权限时重复此规则，不崩溃。

### 5.5 系统电话边界

- 使用安全构造的 tel URI，例如 Uri.fromParts("tel", validatedNumber, null)，不把任意输入直接作为 Intent URI。
- 捕获 ActivityNotFoundException、SecurityException 及可恢复的系统调用失败，转为用户可读状态。
- 不通过隐藏 API 或 AccessibilityService 自动按系统电话按钮。
- 不请求成为默认拨号器，不实现 InCallService、呼叫录音或本应用挂断。
- 无 SIM、欠费、无服务、飞行模式、双卡选择由系统及运营商处理；本应用不能据此声称“已接通”或“对方没接”。
- 紧急号码可能被系统转交拨号确认，不绕过平台限制；V1 不定位成 SOS 或紧急救援应用。
- 不读取通话记录，不根据返回事件估算真实通话时长。
- 本应用的红色“取消”只取消尚在应用内的操作；电话已交出去后，它不能挂断系统通话。

## 6. 联系人校验、编辑与排序

### 6.1 姓名规则

去掉首尾空白后，必须有 1～12 个 Unicode 码点。禁止内部换行、控制字符及无效 Unicode 序列。保留正常中文、字母、空格和用户有意输入的称呼。不得只按 UTF-16 长度计算中文扩展字符或 emoji，也不自动截断超长名字。

### 6.2 号码规范化

规范化是应用行为，不能把语法通过等同于运营商号码真实有效。

1. 先去掉首尾空白。
2. 做 Unicode NFKC 规范化，使常见全角数字、加号、括号能被正常识别。
3. 只去除号码中的普通空格／不换行空格、短横线、左右圆括号。
4. 剩余必须满足：开头可有一个 +，之后为 3～20 个 ASCII 数字。
5. 拒绝内部换行、字母、多个 +、斜杠、星号、井号、逗号、分号、URI scheme 及其他字符。
6. 不自动添加 +86，不删除用户明确填写的国家码，不把所有号码裁成 11 位。
7. 数据库存储规范化后的字符串；家属确认保存前能够看到它。

V1 不支持分机暂停串、USSD/MMI、SIP 或多个号码拼成一个字段。需要另一个号码时，家属另建清楚命名的卡片；不能让老人点击后再选。

### 6.3 添加与编辑

- 新建 UUID，保存文字和规范化照片必须在同一事务中完成。
- 联系人达到 500 时不能再新增；提示当前数量，编辑已有联系人不受影响。
- 名称、号码或照片校验失败时不改数据库，保留可修改的草稿。
- 同号／同名提醒只是家属信息提示，不擅自合并或删除。
- 新联系人追加到末尾。编辑不能改变排序或 ID。
- 换照片成功后更新哈希，清除该联系人旧缓存；不继续显示旧头像。
- 删除照片只删除照片记录，保留联系人及占位色。
- 删除联系人必须明确确认；同时删除照片，剩余 sortOrder 压紧为连续值。
- 保存、删除、排序事务成功后 contactsRevision 加 1；失败不增加。

### 6.4 排序

上移／下移只与相邻联系人交换位置，在单个事务内完成。数据库的 sortOrder 不建立会阻碍交换的唯一索引，但仓储必须维持连续且不重复的业务约束。

禁止按最近拨打、字母、生日、更新时间或使用频率自动重排首页。系统通讯录初次导入的顺序也必须在预览中明确，提交后固定保存。

## 7. 照片处理与持久化

1. 用户通过系统文件选择器选择照片，不申请全盘存储权限。
2. 读取时检查实际字节、文件签名、可解码类型与像素边界，不信任扩展名。
3. V1 保证 JPEG、PNG、静态 WebP；不支持的 HEIF／动画格式给出明确换图提示，不假装导入成功。
4. 先读取图像尺寸，再进行采样解码；禁止为缩略头像一次解码 2400 万像素原图。
5. 根据 EXIF 处理朝向，用裁切组件得到家属确认的方形画面。
6. 标准化至边长不超过 512 px 的 JPEG，并移除原始元数据。
7. 编码策略有明确上限，例如依次尝试 512/质量 82、512/质量 70、384/质量 70、256/质量 70；不放大小原图，取首个不超过 128 KiB 的结果。仍不满足则报错，不能无限循环。
8. 计算最终字节 SHA-256，在联系人保存事务中写入照片表。
9. 外部 content URI 只用于本次读取；最终显示不能依赖源相册、提供者授权或原文件存在。
10. 取消选图、裁切或联系人编辑都不替换旧照片；清除不再使用的临时文件。
11. 导入备份照片先验证文件哈希，再作安全解码和同样规范化；存储哈希按最终字节计算。视觉和内容保持一致，不要求 JPEG 重编码后逐字节相同。

## 8. 手机系统通讯录批量导入

### 8.1 来源权限

只在家属选择该功能时申请 READ_CONTACTS。只读 ContactsContract，不申请 WRITE_CONTACTS，不修改或删除系统通讯录。以后系统通讯录发生变化也不会自动改动 App 内的卡片。

### 8.2 选择与预览

- 以系统联系人分组，一人多个号码时明确让家属选一个。
- 只有一个号码可直接预选；多个号码只有系统明确标记主号码时可默认选它，否则必须选择。
- 预览显示来源姓名、选中号码、照片、将使用的称呼与校验结果。
- 全选不跳过号码歧义：必须解决或取消选择有问题的人。
- 超长名称不能自动截短；允许家属修改称呼后重新校验。
- 无号码、无效号码项不可提交；缺照片可以在家属知情下使用占位图。
- 系统照片读取失败不导致删除现有数据；在预览中单独标记缺照片。
- 新卡片数量加已有卡片数量不得超过 500。
- 重复号码以**导入开始前目标机的号码集合**判断，匹配则默认跳过并保留现有卡片。
- 来源中不同人共用同一号码，可作为不同选中对象保留；预览须提醒，不能静默合成一个人。
- 预览顺序确定为当前界面展示顺序，提交后按该顺序追加。

### 8.3 提交

提交前完成所选有效条目的照片规范化，创建新的 UUID。在一个 Room 事务内添加所有选中且未被跳过的条目、照片及顺序。任何存储错误全部回滚。

结果分别报告新增、跳过、用户取消选择数量。拒绝权限或取消选择不改变现有联系人。系统来源 ID 不作为跨设备可移植身份，也不写入导出文件。

## 9. 联系人交换文件协议 v1

### 9.1 文件容器

- 文件名建议：SilverPhone_联系人_YYYYMMDD_HHmmss.zip，时间取本机时间；文件名只供人阅读。
- MIME 为 application/zip；选择器返回未知 MIME 时仍以内容验证决定，不只看后缀。
- 使用标准 ZIP，未加密；不发明伪 ZIP、自定义压缩算法或密码包装。
- 本文件是联系人交换包，不是 Room 数据库备份；禁止直接复制数据库及 WAL 文件代替。
- 容器中只允许 manifest.json 和清单明确引用的 photos/<contactId>.jpg 条目。导出时不写额外目录条目。

~~~text
SilverPhone_联系人_20260917_160000.zip
├── manifest.json
└── photos/<联系人UUID>.jpg    # 可选，每个有照片的联系人一个文件
~~~

### 9.2 清单字段

| 字段 | 必须 | 规则 |
|---|---|---|
| format | 是 | 固定为 silverphone-backup |
| schemaVersion | 是 | 整数 1；任何其他版本拒绝，不猜测兼容 |
| exportedAt | 是 | ISO 8601 UTC 时间，形如 2026-09-17T08:00:00Z |
| appVersion | 是 | 导出程序版本字符串，只作说明，不能代替协议版本 |
| contacts | 是 | 按 sortOrder 排列的数组，1～500 条 |

每条联系人字段：id、displayName、phoneNumber、sortOrder、placeholderColor、photo。前五项规则同领域模型。photo 无照片时必须为 null；有照片时为以下对象：

| photo 字段 | 规则 |
|---|---|
| path | 严格等于 photos/<本联系人id>.jpg |
| mimeType | 固定 image/jpeg |
| byteCount | 原始归档照片的实际字节数，1～131072 |
| sha256 | 原始归档照片字节的 64 位小写十六进制 SHA-256 |

SHA-256 用来发现内容损坏，不证明文件发送者身份，也不是加密或数字签名。

}
~~~

有照片的协议测试文件必须用真实生成的测试 JPEG、真实 byteCount 和真实 sha256 制作，不能用虚构哈希声称可导入。

### 9.4 不进入文件的内容

不导出字体档位、系统授权、SIM 选择、联系人集合修订号、数据库自增状态、设备标识、相册 URI、绝对路径、通话记录、缓存、日志、用户未选入本应用的系统联系人。

这是“复制亲人资料”，不是账号同步。导入后两台手机独立变化，后续编辑不会自动传播。

## 10. 导出算法

1. 家属进入导出页，明确本次导出 App 中全部联系人。空列表禁用导出，不生成零联系人替换包。
2. 获取一致的数据快照：联系人元数据、排序及对应照片应来自同一个 Room 读取事务。
3. 逐张读取照片并流式写入私有缓存 ZIP；不一次把全部 BLOB 或完整 ZIP 加载到内存。
4. 写入 UTF-8 清单、照片实际大小与哈希，正常关闭 ZIP。
5. 本地生成成功前，不显示“导出成功”，不打开分享面板。
6. 提供保存／分享。保存使用系统 CreateDocument；分享使用 FileProvider 的 content URI 与临时读取授权。
7. 保存操作先生成完整缓存文件再复制到新建的目标 URI；复制并关闭成功后才能写“已保存”。
8. 文件提供者不保证原子写入。失败时只尝试删除本次新建的不完整目标文件；删除失败则提示可能残留不完整文件，不删除其他用户文件。
9. 打开系统分享面板只能记为“已打开分享”，不能知道接收人是否收到或导入。
10. 分享缓存保留至最长 24 小时后的下一次前台清理；不能立刻删除导致接收程序来不及读取。当前正在使用的文件不清理。
11. 取消和失败不改本地联系人。所有流和临时资源均需关闭。

## 11. 文件导入：预检必须先于写库

### 11.1 预检状态流

~~~text
IDLE → PICKING → COPYING_TO_PRIVATE_CACHE → VALIDATING → PREVIEW
                                                        ↓
                     原数据保持不变 ← ERROR / CANCELLED
PREVIEW → USER_CONFIRMED → COMMITTING → SUCCESS
                               └────→ ERROR（事务回滚）
~~~

选择器取消、预检失败、用户取消预览都不修改数据。只有 USER_CONFIRMED 后才能开始写库。

### 11.2 容器与路径检查

- 限制实际读取的 ZIP 大小；外部提供者无法报告大小时继续有界流式读取。
- 用标准 ZIP 库读取；拒绝加密包、无效压缩方法、损坏 CRC 或读取失败。
- 拒绝重名条目、额外条目、未声明照片、声明但缺少的照片。
- 拒绝绝对路径、.. 路径段、反斜杠路径、盘符、嵌套 ZIP 及不符合白名单的名称。不按归档内容创建或跟随符号链接，只读取协议允许的普通数据内容。
- 不按不可信 entry.name 直接拼接目标文件路径。暂存文件名由程序生成；照片路径只作协议匹配。
- 检查逐项和总解压字节上限，不能只看 ZIP 中声明的未压缩大小。
- 不能依赖新 Android 的 ZIP 路径保护来替代应用在 API 23 上的校验。[Android ZIP 路径风险说明](https://developer.android.com/privacy-and-security/risks/zip-path-traversal)

### 11.3 清单与图像检查

- 使用严格、类型明确的 JSON DTO；拒绝缺失字段、未知字段、类型错误及不支持的 schemaVersion。
- contacts 不为空，条目不超过 500；UUID 不重复、格式规范。
- sortOrder 必须与数组索引一致，正好为 0..N-1，不接受重复、负数和稀疏顺序。
- 姓名、规范化号码、颜色枚举都通过同一业务校验。归档号码必须已经规范化，不能导入时悄悄改成另一串号码。
- 每张图的实际字节数和哈希必须匹配，确认 JPEG 签名、可解码、方形和像素上限。
- 完成图像安全规范化后把待导入照片放在私有暂存区，记录最终大小和哈希。
- 任意一项损坏，整个备份拒绝；不能跳过坏照片然后说全部导入成功。
- 与系统通讯录缺照片不同，文件明确声明一张照片存在但读不到，属于损坏。

## 12. 重复联系人与导入模式的确定规则

### 12.1 模式 A：追加，默认

目标：保留当前老人已经学会的称呼、照片与顺序，只增加新的亲人。

设 T 为预览开始时目标机完整联系人快照，S 为按顺序读取的来源条目：

1. 如果 s.id 已存在于 T：跳过整条来源记录，保留目标记录，即使来源名字或号码发生变化。
2. 若 ID 不匹配，但 s.phoneNumber 在 T 的规范化号码集合中：跳过来源，保留目标机所有已有同号卡片。
3. 两者都不匹配：作为新增项，保留来源 ID、称呼、号码、颜色与照片。
4. 比较集合始终是原始 T，不是逐条加入后的集合。因此空目标机可以完整保留来源文件中不同 ID 但共用同一号码的人。
5. 文件内部 UUID 重复属于无效文件，不能进入本流程。
6. 目标机已有项目保持原顺序；新增项按来源顺序追加并重新分配连续 sortOrder。
7. 同 ID 不同号码计入“身份相同，保留现有”冲突提示；不自动认为号码更新更可信。
8. 添加后若超过 500 条，整个操作停止并提示容量不足，不静默截断。
9. 新增数为零时结果为“没有新增，已保留现有亲人”；不写数据库、不增加修订号。

不用名称匹配身份，不用修改时间决定谁覆盖谁，不执行模糊名字匹配。

### 12.2 模式 B：整体替换，显式选择

- 家属在预览中选替换，再确认删除 M 条、写入 N 条。
- 同一个事务删除所有当前联系人／照片，写入完整来源集合及照片。
- 本机字体档位保留；联系人修订号加 1。
- 不能先删数据库，再在另一个异步流程逐张补图。
- 全部校验在事务前完成。事务中仍遇到空间不足或读取失败，必须整体回滚。
- 未知协议版本、空文件或零联系人包不能用于替换。
- 不自动执行“替换失败后再尝试追加”。

### 12.3 规则例子

| 目标机 | 来源 | 追加结果 |
|---|---|---|
| 没有联系人 | 女儿 A、儿子 B | 新增 A、B，照片顺序保持 |
| ID A，称呼“闺女” | 同 ID A，称呼“姐姐” | 保留“闺女”，不改照片 |
| ID A，号码 X | 不同 ID C，号码 X | 跳过 C，保留 A |
| 没有联系人 | ID A 与 B 共用号码 X | A、B 都新增，因为原始目标为空 |
| 已有 A、B | 再导入同一文件 | 新增 0，顺序和照片不变 |
| ID A，号码 X | 同 ID A，号码 Y | 跳过并提示冲突，不替换成 Y |
| 已有 499 位 | 文件有 2 位全新亲人 | 拒绝整次新增，不只导入第一位 |

## 13. 并发、事务与进程死亡

- 联系人写操作通过一个仓储入口串行化；不要每个页面各自直接修改数据库。
- 预览记录 expectedRevision。确认提交时在事务中检查当前 contactsRevision。
- 修订号变化说明预览已过期，停止提交、重新生成预览，让家属确认新数量；不能沿用旧的覆盖范围。
- 事务只读取已在私有目录验证完成的资源，不在写事务内等待外部文件选择器、网络或用户输入。
- 正式提交阶段禁用重复点击；数据库异常／协程取消在提交完成前触发回滚。
- 如果进程在提交后、结果页面显示前被杀，下次启动以数据库为准，不声称上次失败后重新执行。
- 不能把整个 ZIP 或照片集合放入 Bundle、SavedStateHandle 或导航参数。
- 预检／裁切被杀后可以要求重新选择，不把恢复复杂工作流作为 V1 必做功能。
- 共享文件临时授权、未完成暂存目录和未使用草稿在有界清理流程中移除；不清理活跃操作。
- 列表 Flow 只发布已提交的完整状态；不能先把 UI 乐观改成“全部成功”再等落库。

## 14. 本地隐私与文件生命周期

默认不联网、不收集分析数据、不写完整号码或照片到日志。导出文件本身未加密，提醒家属只发给可信对象。不能把明文 ZIP 标成“加密备份”。

联系人和照片保存在应用私有数据库；系统文件选择器或分享目标可能属于云服务，是否使用由家属选择。本应用的离线性质不代表用户选中的外部服务永远离线。

按技术文档显式配置 Android 备份／设备传输排除规则，不依赖默认系统云备份。不同厂商的系统迁移行为应以实测说明，不作不可验证的绝对承诺。

## 15. 必须实现的边界测试

以下是有真实业务风险的测试，不是为每个字段写机械重复测试：

1. 连点同一张卡 10 次、快速点不同卡、重组和 Activity 重建，各自不能产生重复拨号。
2. 权限未授予、拒绝、永久拒绝、被系统撤销；重新授权后不自动拨打。
3. 中文名字、扩展字符、空名字、12/13 码点边界；号码全角、国际前缀、座机、非法控制符。
4. 同名不同号、同号不同名、同 ID 变更号码的追加规则。
5. 添加／替换照片后删除源相册文件、重启应用，头像仍正常。
6. 系统通讯录多人、多号码、缺照片、超长名、权限中途撤销。
7. A 导出 → B 导入：照片、称呼、号码和顺序保持；B 字号不变。
8. 同一包重复追加 3 次：第二次起新增为零，不产生重复卡。
9. 替换模式在照片写入中途、容量不足和协程取消下失败：旧联系人与旧照片全部保留。
10. 有额外条目、重复条目、路径穿越、超大文件、解压超限、图像超限、错误哈希、缺照片、未知版本：拒绝且数据库不变。
11. 外部提供者无法报告大小、断流、返回错误、用户取消：不会误报成功。
12. 提交前修订号改变：必须更新预览，不能沿用旧确认。
13. 文件写入成功但分享取消：联系人不变；只显示与实际完成程度一致的结果。
14. 进程在预检、提交前、事务中、提交后被终止：启动后只出现完整旧集合或完整新集合。
